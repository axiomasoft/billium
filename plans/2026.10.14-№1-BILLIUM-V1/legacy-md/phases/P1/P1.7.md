### P1.7 — Контракты v1, план fixtures и каталог приёмки

**Intent:** Описать `billium-contracts` v1:
- команды и исходы оплат и возвратов, совместимые с envelopes пилота `payment.execute.v1` /
  `payment.outcome.v1`;
- приём usage/overage-фактов;
- obligation/invoice queries;
- события и receipts;
- ошибки.

К контрактам приложить план language-neutral fixtures для PHP и Dart. Отдельно собрать каталог
приёмки — сторону Billium из PB, PF, MG, FD, SB, EC, с N-процессными concurrency-тестами и
restore/clone/lost-response.

**Why:** P2 начинается с `billium-contracts` для PHP и Dart и conformance fixtures. Без
зафиксированной формы и каталога приёмки P2 не знает, что генерировать и чем проверять, а P3–P9 — что
считать «готово». Совместимость с пилотом Commerz↔Billium — граница CD-02. RAG:— (repo-grounded:
`brief/00-owner-message.md` §3 пп. 7–8; `research/P1-sources.md` § 5 «Оплата и исполнение»).

**Scope Included:**
- `docs/contracts/billium-contracts-v1.md`:
  1. `## Принципы` — MoneyWire CD-05 (decimal string + ISO 4217, без float), idempotency key + digest
     и conflict, versioning `*.v1`, problem-codes;
  2. `## Оплаты и возвраты` — команды и исходы; таблица `Поле пилота | Поле Billium | Совместимость`
     для `payment.execute.v1` и `payment.outcome.v1`;
  3. `## Usage и overage` — входной контракт по CD-15 (Billium не импортирует Tariffler);
  4. `## Obligations и invoices` — queries;
  5. `## События и receipts` — разделение транспортного ACK и бизнес-receipt;
  6. `## Ошибки` — таблица `Код | Когда | Повторяемо | Действие клиента | Основание`;
  7. `## План fixtures` — таблица `Набор | Что проверяет | PHP | Dart | Оракул`; vectors/golden по
     `methods.json`;
  8. `## Трассировка` — таблица `Элемент | Основание`: каждая команда, исход, query, событие и receipt
     из разделов 2–5 с разрешимыми REQ/INV/D/CL/DR0N-ID (D7). Элемент без основания не вводится.
- `docs/acceptance-catalog.md`:
  1. `## Пилот PB` — строки `PB-01…PB-24`;
  2. `## Prerequisites PF` — строки `PF-01…PF-14`;
  3. `## MG, FD, SB, EC` — все MG-01…12, FD-01…10, SB-01…10, EC-01…12 из `research/P1-acceptance-inventory.md`;
  4. `## Concurrency (N процессов)`;
  5. `## Restore, clone, lost response`;
  6. `## Покрытие требований` — описан ниже.
  Колонки: `ID | Сценарий | Сторона | Фаза | Требования | Контракт | Примечание`. «Сторона» ∈ `billium | сосед:<имя>
  | n/a`; для не-billium — причина. «Требования» — существующие REQ/INV-ID из `docs/requirements.md`.
  Concurrency- и restore-строки получают ID `ACC-CON-NN` и `ACC-RST-NN`.
  Для не-billium обязательны объяснение в «Примечание» и REQ-OUT/REQ-NBR. Для billium обязательны
  фаза P2–P10 и контракт/якорь модели. Смешанный сценарий сохраняет сторону Billium и отдельно
  описывает обязанность соседа; отсутствие одной стороны не делает весь сценарий n/a.
  Раздел «Покрытие требований» включает каждый REQ/INV из актуального requirements:
     `ID | Диспозиция | Сценарии | Основание`; `учтено` → существующие ID каталога;
     `вопрос владельцу|вне границ` → объяснение с REQ/INV/D#. ID нельзя пропустить.
- В плане fixtures перечислить положительные и отрицательные примеры MoneyWire (precision,
  scale, rounding, invalid currency, large values), same/changed digest, canonicalization,
  неизвестный исход, duplicate/reorder, error codes, UTC boundaries и старую совместимую версию.
  Конкретные правила берутся из D#/первичных источников; P2 создаёт исполнимые vectors.
- В контрактах явно определить seller/account scope и caller context, identity/revision,
  retries/query/recovery, ordering/duplicate semantics, compatibility/versioning и поля,
  которые запрещено передавать (credentials/secret binding). Для каждой FSM outcome — wire mapping.
- Для каждого ACC-CON указать N и барьеры/порядок действий, начальные данные, допустимые исходы,
  проверяемый INV и ожидаемый DB proof. ACC-RST фиксирует checkpoint, потерянный effect/reply,
  recovery barrier и условие возобновления. Реальные тесты принадлежат будущим фазам.

**Implementation Rules:**
- risk-class: data-integrity
- invariant-model: research/P1-design.md
- Контракт описывает форму и семантику и не содержит реализации.
- Имена полей пилота сохраняются. Расхождение — только с колонкой «Совместимость» = `breaking` и D#.
- Каждая команда, меняющая деньги, имеет idempotency key, digest и явный исход `unknown`.
- Refund ссылается на исходный charge и его исполнителя.
- Dart в контрактах — клиент: команды и queries формирует, денежных записей не делает.
- Каждый PB и PF из паспортов присутствует в каталоге. Если ID в паспорте отсутствует или
  переименован, это записывается в строке `n/a` с причиной, без пропуска.

**Code Guidance:** Описывать поля таблицами `Поле | Тип wire | Обязательно | Семантика`, без
псевдокода. Суммы — `string` decimal + `currency` ISO 4217. Время — RFC 3339 UTC. Каталог приёмки —
одна строка на сценарий, формулировка «дано / когда / тогда» сжата в одну фразу.
