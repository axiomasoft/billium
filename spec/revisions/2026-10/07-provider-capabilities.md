# Provider capabilities and execution SPI

[BC-CAP-01] Owner execution: payment.capabilities.v1 pins normalized driver/provider/API versions, payment-method family, provider key scope and guaranteed TTL, lookup selector/visibility/completeness/retention, authorization, capture and provider void modes, partial/multiple refunds, callback authenticity/event identity, inventory, settlement, disputes, saved method, recurring consent and fiscal passthrough. unsupported and unverified refuse before operation, attempt, reservation or network dispatch; billium.capability.unsupported has receipt none and preserves the command identity. Provider retention expiration never certifies absence. (D57, D31, REQ-OWN-21)

[BC-CAP-02] Owner contracts: payment.execute.v1 remains sale; payment.authorize.v1 establishes a charge root with executionMode authorize. payment.capture.v1 and payment.void_authorization.v1 are separate keyed child operations with their own operationRef different from originalOperationRef and frozen root binding. payment.cancel.v1 remains local unsent cancellation. payment.admission.v1 and its CommandAccepted receipt apply to new commands; transport ACK is never a business receipt. Existing charge/refund kinds and operation statuses remain strict. payment.effect.outcome.v1 and its negotiated events-2026-10-v2 catalog are consumed unchanged from P3.4; child effectTotal is cumulative actual evidence, never a root total or ledger delta. (D57, D26, D37, D41, D63)

[BC-CAP-03] Owner execution: payment.driver_lookup.v1 separates found, unavailable, ambiguous and certified_absent. Certified absence requires exact account/environment and selector/value coverage, complete provider horizon covering every possible old dispatch, retained history and independently verified old-dispatch fencing proof. Timeout, generic HTTP 404, elapsed TTL, local leases and copied epochs cannot construct a certificate. A certificate DTO carries evidence, not authentication: the recovery owner verifies the provider completeness and external fence before accepting it. All lookups are read-only and unsupported lookup retains recoveryRequired. The existing payment.find.v1 stays unchanged. (D54, D57, D62, REQ-FAIL-08)

[BC-CAP-04] Owner execution: payment.qualification.v1 binds the exact capability digest and driver/provider/API versions, dated versioned source URLs, evidence refs, account-continuity/credential-rotation behavior and unresolved gaps. simulated evidence is test-only; sandbox evidence does not enable production. Production eligibility requires a production qualified manifest with no unresolved gaps, and still requires the host's independent WriterAdmission authority. Configuration eligibility does not authorize network calls. Refund/capture/void/recovery always use the root's historical account, never latest routing. (D26, D57, D59, D62)

[BC-CAP-05] Owner contracts: saved-method, recurring-consent, settlement, dispute and fiscal dispositions are explicit capabilities, not assumptions about a payment family such as SBP. Financial writing remains PHP-only; Dart validates/encodes the shared wire and reads outcomes. Ledger paymentStatus already separates applied last consistent, observed actual, financialHold, exposure, spendable, projectionStatus, pendingAllocationReason and reconciliation; provider evidence does not mutate that projection here. (D55, D57, D60, D63, REQ-OWN-18)

[BC-CAP-06] Owner contracts: independent PHP/Dart tests consume the simulated fixture-hmac-sha256 callback body/key/signature vector and reject its wrong-signature and altered-account-body controls. This fixture scheme has no claimed PSP applicability; production callback algorithms, credentials and account/event identity verification belong to the named adapter qualification gate. No Dart callback receiver or financial writer is introduced. (D57, D59, REQ-CON-03, REQ-OWN-18)
