# Authority routing and ledger handoff

The consumer owns execution routing and the inventory of existing business intents. The source and target deployment owners supply authority evidence for ledger handoff. Platform owns the routing journal, the typed evidence and the handoff checks. [D26, D54, D58, D62, D63]

## Execution routing

**MGATE-01 and CT-20 · D58 / D26 · consumer operator.** Configure an explicitly provisioned PostgreSQL connection named `billium-routing` on storage whose continuity is independent of any ledger backup or clone. Install the platform schema there through version 31. The migration leaves journal write access with the schema owner. Grant journal access separately to the authorized routing host and guard initialization and epoch changes as operator actions. Pause new admissions and initialize the scope from a complete existing intent inventory, including tombstones and unresolved operations. Each inventory row contains the original executor, account, binding revision, operation ref, command key and payload digest. Supply original charges before their refunds. An incomplete inventory holds the routing scope closed.

**MGATE-01 and CT-20 · D58 / D26 / REQ-OWN-21 · consumer caller.** Resolve `AuthorityRouter` from the platform provider. Scope it by installation, seller, environment and intent-owner namespace. Reserve the full binding before network dispatch, using the current route for a new charge. The scope row serializes reservations with the committed compare-and-set epoch barrier. A pre-barrier reservation remains bound to the original route even if dispatch occurs after the barrier. An exact replay returns the saved binding. A changed command key, digest, operation or route for the same business intent is a conflict. For unknown outcomes, keep the same key and use lookup or reconciliation with the original executor. A refund has its own command key and operation ref and inherits the original charge's executor, account, binding revision and epoch. An installation alone has no authority to advance the routing epoch.

## Ledger storage move

**MGATE-03 · D58 / D54 / D62 · source and target operators.** Bind `SourceHandoffHost` and `TargetHandoffHost` before resolving the privileged `AuthorityHandoff` commands. `stage` pins the exact source and target scope in target recovery. The plan names both installations, each `ownerSessionRef`, `deploymentGeneration`, `attachmentGeneration` and `authorityEpoch`, plus seller, environment, books, entity sets and lineages. The source operator closes UI, API, cron, collection, import, admin, background and direct permitted write paths, seals financial admission and drains in-flight root transactions before issuing the `SourceFreezeCertificate`. The certificate binds the plan, `freezeGeneration`, `sealReceiptRef` and seal receipt digest. The host verifies continued exclusion and evidence against authority state outside the restorable ledger. `WriterAdmission` covers outgoing execution and is insufficient evidence for this fence. A worker restart in the same valid deployment session leaves the OwnerSession intact.

**MGATE-04 · D52 / D58 / D63/F06 · source exporter.** Pin retention before exporting a repeatable-read snapshot. Use an immutable `snapshotToken` and snapshot digest, a live lease reference and expiry, and a source-authenticated D52 cursor in `(tx_id, id)` order with `tx_id < pg_snapshot_xmin(pg_current_snapshot())`. The `MigrationManifest` binds these claims, the freeze certificate, full source/target scope, event catalog, subscription, explicit selection and `selectionDigest`. The source verifies the selected retained tail through its terminal safe physical cursor. Empty selected pages can advance that cursor. Check gaps for observation partitions independently. Changed selection requires a new bootstrap or bounded retained-history replay. A missing or expired pin, incomplete tail or scope, token or checksum mismatch leaves the target in recovery or requires rebootstrap. A maximum, equality or ordering comparison of `commit_no` has diagnostic value only.

**COV-557 / COV-AC-557 and MGATE-04 · D53 / D55 / D58 / D63/F06 · target operator.** The replacement/export completeness gate compares counts, exact minor-unit totals and digests per seller and currency for the named selection. Cover obligations and open balances, allocations, captured and refunded facts, reservations, corrections and their lineage, source maps, receipts and tombstones. Verify the snapshot and tail bytes before applying through existing APIs in recovery. Dedupe snapshot/tail overlap by stable economic revision. Preserve original identities and linked corrections. Record durable dispositions and adopt the final cursor atomically with the target reconciliation receipt. This replay creates no PSP call, rerating, cash export or duplicate allocation. The fixture transfers one revision present in both snapshot and tail, verifies it once and refuses a tampered transfer.

**MGATE-05 · D54 / D58 / D62 / D63 · target operator.** `activate` is a separate privileged action. Authenticate the exact manifest and target receipt binding, a `RetirementProof` for the old OwnerSession, and an `ActivationCertificate` for the exact target deployment and selected source lineage. The host verifies stopped producers, retired workers, revoked egress and in-flight requests, plus applicable provider inventory and unresolved-effect, namespace and feed dispositions. Recheck source seal, attachment and live retention pin at the exclusive target admission boundary. Serialize this transition with target fencing for rollback. Use the local financial session activation command with its own verified local predecessor evidence where a separate installation requires it. Keep source ledger admission sealed. Host evidence setup, acquisition and network operations run outside Billium root transactions. A restored or cloned attachment or a lost authority continuity enters recovery until it has current scoped evidence.

**MGATE-05 · D54 / D58 / D62 · source operator.** Retiring or releasing one writer seals that session. Before the target's first monetary commit or external effect, rollback requires fencing and draining the target and obtaining authenticated proof that it produced zero monetary commits or effects and cannot reacquire admission for the plan. Resume the source in a new epoch through explicit D54 retirement and lineage activation. Count a monetary commit during recovery apply as a target write. After the first write or effect, continue recovery or run a separately certified reverse handoff. Old execution bindings survive either outcome.

## Evidence and activation inputs

**D59 / D63/F06 / D71 · Platform.** The local proof is the hashed `billium.migration.handoff_evidence.v1` fixture under `fixtures/integration/import/schema/handoff`. The fixture adapters reproduce it in `MigrationEvidenceTest`, and `AuthorityCutoverTest` exercises the committed routing journal on PostgreSQL. The `--handoff` checker validates evidence shape, content digests, scope, lineage, lease time and proof cross-links for these offline migration artifacts.

**D58 / D59 / D62 · deployment owners.** Live activation requires an owner-approved selection and mapping, the actual source host's authenticated freeze, source seal receipt and lease, target verification and adopted cursor, external retirement and lineage activation authorization, and applicable live consumer and provider qualification. The fixture proves the local contract and failure paths. Owners attest production mutator coverage, fencing, retention, backup/restore and recovery readiness separately.
