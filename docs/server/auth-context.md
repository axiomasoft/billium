# Server auth context

The deployment binds `Authenticator`, `SellerContextResolver`, `SellerEligibility` and `AuthorizationVerdict`. `Authenticator` authenticates the request headers and metadata. The resolver takes the authenticated principal and a route seller selector, and returns the seller, installation, environment, actor and grants established by host policy. The Server requires scope agreement with the selected wire envelope and any operation selector in the route. The verdict receives the schema action, exact seller scope, resolved actor, resource selectors and the full semantic digest from the contracts codec. (D9, D23, D32, COV-297, COV-509; owners host, Server and contracts.)

The host owns durable seller IDs, environments and seller eligibility. `SellerEligibility` returns current admission for the exact `SellerScope`. A missing record, ineligible seller or differently scoped result denies delivery. The Server checks admission and the current verdict before delegating any request to a core handler or repository, including a command with an already stored receipt. `billium.auth.unauthenticated` is HTTP 401. Scope and action denials, and a missing resource in an authorized scope, share the same HTTP 403 `billium.auth.denied` response with `receipt: none`. Each core lookup uses the authenticated scope. Account and seller bindings on cursors are verified by the owning query module. (D23, D31, D60, COV-048–050, COV-497; owners host, Server, ledger and platform.)

Capabilities describe supported operations and schema versions. The host issues permissions and execution-profile authorities explicitly. Observation intake grants and execution-profile authorities are independent host policy inputs. (D57, D61, D63; owners host, execution and Server.)

## Host policy inputs

| Boundary | Host input and owner |
| --- | --- |
| Legal seller and documents | `SellerConfiguration` supplies the requested immutable legal and requisites revision and associated tax and fiscal profile snapshot refs. The same port supplies an explicit currency allow-list and numbering-series mapping scoped to seller, document kind and period. The host maps these inputs to the relevant module ports and the documents module owns issuance. (D23, D55, D63, COV-375–376, COV-386; owners host and documents.) |
| Billing accounts and usage | `UsageAttributionResolver` resolves event-time host terms for the authenticated principal, context and source/subject selectors. `ExternalUsageAttribution` records separate source, subject, payer, customer, billing account and actor refs under an explicit seller and mapping revision. A missing mapping leaves attribution unresolved. The host supplies the event-time mapping to the usage module's `UsageAttribution` port. One payer or customer can have seller-specific accounts, balances and mandates. (D23, D60, COV-163, COV-386, COV-531; owners host, usage, ledger and execution.) |
| Merchant configuration | `SellerConfiguration` resolves the exact seller-scoped merchant revision and account ref. Execution retains the original binding, including after the host changes default routing. It owns reads of the immutable binding and the checks on its historical credential continuity. (D57, D58, COV-377; owners host and execution.) |
| Credential resolution | The deployment implements execution's `MerchantCredentials` SPI and authorizes the original installation, seller, environment, merchant revision and purpose before it accesses the secret store. A historical action requires explicit recovery permission for that context. The host resolves the locator from the authorized revision, isolates the seller's key, fails closed and redacts the locator from audit output. HTTP schemas reject locator fields. Deployment owns encryption keys. (D57, D58, COV-383–384, COV-497; owners host, deployment and execution.) |

## Observation intake

`ExecutionContext.sourceAuthorities` carries grants selected by authenticated host policy. An observation must match one grant end to end on channel, authority, installation, environment, seller, lineage and partition before custody, duplicate lookup or receipt disclosure. The grant covers ordinary intake for one exact lineage. Bootstrap and lineage changes require the core recovery path. The core keeps the compound custody namespaces separate and enforces the immutable operation owner when it applies an authenticated observation. (D60, D63, HTTP-21; owners host, Server, platform and ledger.)

`paymentStatus` reads the ledger projection in each supported profile. The applied snapshot, observed provider totals, exposure, hold and `projectionStatus` remain visible when execution is disabled. (D57, D61, D63; owners ledger and Server.)
